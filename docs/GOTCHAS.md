# Gotchas

Traps that are still armed, and the rule each one forces. Remove an entry when
the trap is gone.

- **Workers Free allows five cron triggers per account, not per Worker.** Other
  Workers in this account hold most of them, so a deploy with more than one cron
  fails with code 10072 *after* uploading the script — "partially updated".
  Rule: Orrey has exactly one cron (`* * * * *`); `src/cron/scheduled.ts`
  derives everything else from the time.
- **A table rebuild generated by `drizzle-kit` can silently fill new columns with
  their own names.** When a migration both adds columns and changes a constraint,
  drizzle-kit rebuilds the table and writes
  `INSERT INTO __new_x(<every new column>) SELECT <every new column> FROM x` —
  naming columns the *old* table does not have. SQLite does not reject that: an
  unresolvable double-quoted identifier degrades to a string literal, so every
  existing row is given the literal text `'game_id'`, `'interval_weeks'`, and so
  on. No error, no warning, and the rows are wrong. Rule: when a generated
  migration contains `INSERT INTO __new_…SELECT`, cut every column the migration
  is adding out of *both* lists and let the defaults do their job.
- **`drizzle-kit` drops `ON DELETE` when it adds a column.** A new foreign key on
  an existing table is emitted as `ALTER TABLE x ADD y text REFERENCES z(id)`
  with the referential action silently missing, so `schema.ts` says `set null`
  and the database does `no action` — and the delete fails at runtime instead.
  SQLite accepts the clause on `ADD COLUMN` as long as the default is NULL.
  Rule: after generating a migration that adds a foreign key, read the SQL and
  put the action back. A test that deletes the parent row is what catches it.

- **Never let a migration rebuild a table that something references.** SQLite
  cannot add or change a constraint in place, so drizzle-kit rebuilds the table:
  `PRAGMA foreign_keys=OFF`, create `__new_x`, copy, `DROP TABLE x`, rename. In
  D1 that `PRAGMA` does nothing — the drop fires `ON DELETE CASCADE` on every
  child row, and the migration reports success. Rebuilding `campaigns` would
  empty `sessions`, and `attendance` and `calendar_links` behind it. Proved
  against the real D1: parent rebuilt, child went from 1 row to 0.
  `PRAGMA defer_foreign_keys` does not help either. Rule: a referenced table
  grows only by `ALTER TABLE ADD COLUMN`; if a constraint is genuinely needed,
  enforce it in the code that writes the column. Note that
  `0003_campaign_state_fails_closed.sql` is already this shape — check a copy of
  the remote database before running it there.

- **A table rebuild generated by `drizzle-kit` can silently fill new columns with
  their own names.** When a migration both adds columns and rebuilds, drizzle-kit
  writes `INSERT INTO __new_x(<every new column>) SELECT <every new column> FROM
  x` — naming columns the *old* table does not have. SQLite does not reject that:
  an unresolvable double-quoted identifier degrades to a string literal, so every
  existing row is given the literal text `'game_id'`, `'interval_weeks'`, and so
  on. No error, and the rows are wrong. Rule: if you ever have to hand-write a
  rebuild, cut every column the migration adds out of *both* lists.
- **Adding weeks in seconds moves the clock, not the date.** A fortnightly 19:00
  game stepped forward as `+ 14 * 86400` becomes an 18:00 game the moment the
  series crosses a DST change, and stays wrong until the next one. Days are not
  a fixed number of seconds. Rule: recurrence steps in *calendar days* in the
  guild's zone (`src/campaigns/recurrence.ts`), converting back to an instant
  afterwards; dividing elapsed seconds by an interval has the same bug and drifts
  further the older the anchor is.
